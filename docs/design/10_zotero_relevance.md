# Zotero-Based Personal Relevance

## 1. Decision

Use Zotero as the user's personal literature corpus, not as a manually curated profile system.

The first version should not require the user to label collections as `core`, `background`, or `low-priority`. For each external candidate, the system retrieves the most related Zotero items and asks an agent to judge personal relevance from evidence.

## 2. Input Format

Use Better CSL JSON as the first supported Zotero export format.

Reasons:
- It is structured enough for reliable parsing.
- It avoids coupling to Zotero's local SQLite internals.
- It can be regenerated by Better BibTeX automatic export.
- It preserves enough metadata for first-pass relevance: title, authors, venue, date, DOI, URL, abstract, tags, and notes when available.

Current implementation also supports Zotero Web API / Local API as a read-only corpus source. Configure either:
- `ZOTERO_CSL_JSON`
- `ZOTERO_USER_ID` or `ZOTERO_GROUP_ID` with optional `ZOTERO_API_KEY`
- `ZOTERO_API_BASE_URL=http://127.0.0.1:23119/api` and `ZOTERO_USER_ID=0` for Zotero Desktop Local API
- `ZOTERO_MAX_ITEMS` to control the Zotero API item cap; default is 2000

## 3. Target Flow

```text
external candidate
  -> normalize artifact
  -> retrieve top-k similar Zotero items
  -> enrich candidate with author/group/venue quality evidence when available
  -> first-pass deterministic display gate
  -> later: agent relevance judge
  -> score_breakdown personal relevance hints
  -> triage/report consumption
```

## 4. Agent Judgment Contract

The agent should only receive the candidate plus retrieved Zotero evidence, not the full Zotero library.

RR-027 implements the deterministic first pass before the agent judge:
- tokenize candidate title / abstract / summaries / tags / authors
- retrieve top-k Zotero items with token cosine similarity
- write the top match score and evidence into `score_breakdown`
- hide already evaluated academic artifacts below the configured Zotero similarity threshold only when no LLM judge result exists

RR-032 implements the LLM judge layer:
- prompt receives only the candidate paper and top-k Zotero evidence
- LLM decides whether the candidate is truly relevant, instead of treating token cosine as final relevance
- judged papers are displayed only when `academic_relevance_relevant=true` and `academic_relevance_score` meets the stored threshold
- the raw `zotero_similarity` threshold becomes fallback behavior for unjudged papers

Expected structured output:

```json
{
  "relevant": true,
  "relevance_score": 0.82,
  "reason": "中文一句话说明",
  "matched_zotero_titles": ["Related Zotero item"]
}
```

The output can later feed triage, but current behavior only uses it as a strict display relevance gate. Final bucket assignment remains a reporting/triage responsibility.

## 5. arXiv Quality Bias

For arXiv, use a conservative policy: quality over coverage.

High-priority arXiv recommendations should require both:
- clear relationship to retrieved Zotero items
- credible quality evidence from authors, groups, venues, institutions, citations, prior top-conference publications, artifacts, or comparable signals

Weak quality evidence should prevent an arXiv item from entering `read_original` or `detailed_summary`, even when topical similarity is high.

RR-027 implements the first quality signal with CSRankings faculty data:
- local CSV via `CSRANKINGS_CSV`, or public CSV via `CSRANKINGS_URL`
- exact normalized author-name match against CSRankings faculty records
- matched faculty evidence is stored with affiliation/homepage/scholar id when available
- evaluated arXiv artifacts below `academic_quality_min_for_arxiv` are hidden from display surfaces

This is intentionally conservative and incomplete: it prefers not showing weakly evidenced arXiv papers over trying to infer group quality from noisy metadata.

## 7. Web Presentation

Web Console paper cards should expose evidence as compact chips, not as another paragraph.

Current chip sources:
- `academic_focus_labels` -> primary focus chips
- `academic_relevance_score` -> `相关度 0.xx` chip, LLM judge reason in tooltip
- `academic_quality_signals.matched_faculty` -> CSRankings faculty / group chips

If `academic_focus_labels` are present, the card should not show raw Zotero categories or related paper titles. If labels are absent, the card may fall back to a small number of non-generic artifact/Zotero topics.

Zotero match evidence should store at most 3 topic keywords per matched Zotero item. Paper cards should prefer Chinese `summary_l3` so the card remains summary-first; if `summary_l3` is unavailable, fall back to Chinese `summary_l1`. If no Chinese summary exists, the card may synthesize a Chinese focus sentence from `academic_focus_labels` instead of exposing the English abstract.

## 8. Non-Goals

- Do not require manual collection labeling before the feature is useful.
- Do not read the Zotero SQLite database directly.
- Do not parse PDF full text in the first version.
- Do not send the full Zotero library to an LLM prompt.
- Do not merge academic and industry rankings.
- Do not let arXiv topical similarity alone produce a must-read recommendation.

## 9. Open Parameters

Initial defaults:
- Zotero export format: Better CSL JSON
- Retrieval evidence size: top 5 Zotero items per candidate
- Zotero API max items: 2000
- LLM relevance display threshold: 0.6
- arXiv policy: conservative / high precision

Parameters to tune after first runs:
- similarity threshold
- top-k size
- daily arXiv high-priority cap
- trusted institution / group signals
- metadata provider fallback order
